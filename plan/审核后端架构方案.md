# 审核后端构建方案（Node.js + Express + PostgreSQL）

## 1. 方案目标
本方案用于指导后端团队在不了解前端内部实现的情况下，独立完成“审核前端”所需后端服务。

约束来源：
- `plan/审核后端构建prompt.md`
- 当前已实现前端的真实接口契约（`src/services/api/qa.api.ts`）

本方案重点：
- 先保证接口契约 100% 对齐，前后端可立即联调
- 再扩展登录鉴权、审核日志、权限控制

---

## 2. 技术栈与部署边界

- Runtime: Node.js 20+
- Web Framework: Express.js
- DB: PostgreSQL 15+
- Auth: JWT（`jsonwebtoken`）
- 密码哈希: `bcrypt`
- SQL 驱动: `pg`
- 参数校验: `zod` 或 `joi`
- 迁移工具: `node-pg-migrate` / `knex`（任选其一）

部署建议：
- 后端服务端口：`8080`
- API Base URL：`/api/v1`
- 前端联调 URL：`http://localhost:5173`

## 4. 数据库设计

## 4.1 用户表（按 prompt 强制）

```sql
CREATE TABLE users (
  id            BIGSERIAL PRIMARY KEY,
  username      VARCHAR(64) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  name          VARCHAR(100) NOT NULL,
  role          VARCHAR(16) NOT NULL CHECK (role IN ('admin','reviewer','observer')),
  status        VARCHAR(16) NOT NULL DEFAULT 'active' CHECK (status IN ('active','disabled')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 4.2 QA 主表（前端主契约）

```sql
CREATE TABLE qa_pairs (
  id            UUID PRIMARY KEY,
  question      TEXT NOT NULL,
  answer        TEXT NOT NULL,
  topics        TEXT[] NOT NULL DEFAULT '{}',
  scenes        TEXT[] NOT NULL DEFAULT '{}',
  confidence    NUMERIC(3,2) NOT NULL CHECK (confidence >= 0.5 AND confidence <= 1.0),
  status        VARCHAR(16) NOT NULL CHECK (status IN ('pending','reviewed','deprecated')),
  reviewer      VARCHAR(64),
  reviewed_at   TIMESTAMPTZ,
  review_notes  TEXT,
  version       INT NOT NULL DEFAULT 1
);
```

## 4.3 片段表与关联表（详情页必需）

```sql
CREATE TABLE fragments (
  id            UUID PRIMARY KEY,
  fragment_type VARCHAR(16) NOT NULL CHECK (fragment_type IN ('text','code','table','figure')),
  content       TEXT NOT NULL,
  page_start    INT,
  page_end      INT,
  source        TEXT
);

CREATE TABLE qa_fragment_link (
  qa_id         UUID NOT NULL REFERENCES qa_pairs(id) ON DELETE CASCADE,
  fragment_id   UUID NOT NULL REFERENCES fragments(id) ON DELETE CASCADE,
  PRIMARY KEY (qa_id, fragment_id)
);
```

## 4.4 审核操作日志（prompt 强制）

记录“谁审了哪条、改了什么、什么时候改的”。

```sql
CREATE TABLE review_audit_logs (
  id               BIGSERIAL PRIMARY KEY,
  qa_id            UUID NOT NULL REFERENCES qa_pairs(id) ON DELETE CASCADE,
  actor_user_id    BIGINT REFERENCES users(id),
  actor_username   VARCHAR(64) NOT NULL,
  action           VARCHAR(32) NOT NULL, -- assign | review | deprecate | edit
  before_data      JSONB NOT NULL,
  after_data       JSONB NOT NULL,
  changed_fields   JSONB NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 4.5 登出黑名单（建议）

```sql
CREATE TABLE jwt_blacklist (
  jti          UUID PRIMARY KEY,
  user_id      BIGINT REFERENCES users(id),
  expires_at   TIMESTAMPTZ NOT NULL,
  revoked_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## 5. 认证与权限模型

## 5.1 JWT 策略
- 登录签发 Access Token（建议 8h）
- `Authorization: Bearer <token>`
- Token Payload 建议：`sub`、`username`、`role`、`jti`、`iat`、`exp`

## 5.2 权限模型
- `admin`: 全部能力（分配、审核、查看统计、查看历史）
- `reviewer`: 读取 + 审核提交；可“领取到我”
- `observer`: 只读

## 5.3 与当前前端的角色兼容（关键）
当前前端角色枚举是：`admin | reviewer | viewer`。

后端按 prompt 使用 `observer` 时，必须二选一：
1. 后端响应时把 `observer` 映射为 `viewer`（推荐，前端零改动）
2. 修改前端角色枚举为 `observer`

建议采用方案 1，避免前端路由守卫拦截失败。

## 6. API 契约（必须按此返回）

## 6.1 认证接口（prompt 要求）

### POST `/api/v1/auth/login`
请求：
```json
{
  "username": "reviewer-01",
  "password": "123456"
}
```

响应 200（前端至少依赖 `token/username/role`）：
```json
{
  "token": "<jwt>",
  "username": "reviewer-01",
  "role": "reviewer",
  "name": "审核员A",
  "expires_in": 28800
}
```

### GET `/api/v1/auth/me`
Header: `Authorization: Bearer <jwt>`

响应 200：
```json
{
  "id": 2,
  "username": "reviewer-01",
  "name": "审核员A",
  "role": "reviewer",
  "status": "active"
}
```

### POST `/api/v1/auth/logout`
Header: `Authorization: Bearer <jwt>`

响应 200：
```json
{ "success": true }
```

## 6.2 审核接口（当前前端严格校验）

### GET `/api/v1/qa/pending?limit=20`
返回必须是数组：
```json
[
  {
    "id": "uuid",
    "question": "...",
    "answer": "...",
    "topics": ["半导体器件"],
    "scenes": ["engineer"],
    "confidence": 0.95,
    "status": "pending",
    "reviewer": "reviewer-01",
    "reviewed_at": null,
    "review_notes": null,
    "version": 3
  }
]
```

### GET `/api/v1/qa/{id}`
返回对象，且必须包含 `fragments` 数组：
```json
{
  "id": "uuid",
  "question": "...",
  "answer": "...",
  "topics": ["..."],
  "scenes": ["..."],
  "confidence": 0.9,
  "status": "pending",
  "reviewer": "reviewer-01",
  "reviewed_at": null,
  "review_notes": null,
  "version": 3,
  "fragments": [
    {
      "id": "uuid",
      "fragment_type": "text",
      "content": "...",
      "page_start": 12,
      "page_end": 12,
      "source": "Sentaurus Manual"
    }
  ]
}
```

### PUT `/api/v1/qa/{id}`
请求体（前端当前会发送完整字段）：
```json
{
  "question": "...",
  "answer": "...",
  "topics": ["..."],
  "scenes": ["..."],
  "confidence": 0.91,
  "review_notes": "...",
  "status": "reviewed",
  "version": 3,
  "reviewer": "reviewer-01"
}
```

实现要求：
- 版本冲突校验：`payload.version != db.version` 返回 `409`
- 成功后 `version = version + 1`
- `status in ('reviewed','deprecated')` 时更新 `reviewed_at`
- 必须写入 `review_audit_logs`（含 diff）
- 响应返回最新详情对象（与 `GET /qa/{id}` 同结构）

### GET `/api/v1/qa/stats`
```json
{
  "pending": 12,
  "reviewed": 120,
  "deprecated": 4
}
```

### GET `/api/v1/qa-pairs?page=1&page_size=20`
注意：当前前端期望“数组”而非分页包装对象。
```json
[
  {
    "id": "uuid",
    "question": "...",
    "answer": "...",
    "topics": ["..."],
    "scenes": ["..."],
    "confidence": 0.95,
    "status": "reviewed",
    "reviewer": "reviewer-01",
    "reviewed_at": "2026-03-22T08:00:00Z",
    "review_notes": "...",
    "version": 5
  }
]
```

## 7. 审核日志写入规则（必须实现）

每次调用 `PUT /qa/{id}`：
1. 取修改前记录 `before_data`
2. 应用更新得到 `after_data`
3. 计算 `changed_fields`（只记录变化字段）
4. 写入 `review_audit_logs`

`action` 判定建议：
- `status: pending -> reviewed` => `review`
- `status: pending -> deprecated` => `deprecate`
- `status: pending + reviewer变更` => `assign`
- 其他字段编辑 => `edit`

## 8. 错误响应规范

统一格式：
```json
{
  "code": "VERSION_CONFLICT",
  "message": "版本冲突，请刷新后重试",
  "details": null,
  "request_id": "req-xxxx"
}
```

状态码建议：
- `400` 参数错误
- `401` 未登录/Token 无效
- `403` 权限不足
- `404` 记录不存在
- `409` 版本冲突
- `422` 业务校验失败
- `500` 服务器错误
