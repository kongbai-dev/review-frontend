# 文件批处理下一步修改计划（v2）

更新时间：2026-04-13  
适用范围：`testagent/backend_api`

## 1. 目标变更（基于最新讨论）

1. `knowledge_data` 不再按业务类型分子目录。
2. 本地文件只分两类目录：
   - `knowledge_data/docs/`
   - `knowledge_data/csv/`
3. 保留两种上传模式：
   - `sync`：单对上传（文档 + CSV），上传后立即同步 MinIO。
   - `batch`：支持前端批量上传文档与 CSV（分两个接口），由前端手动触发批处理同步 MinIO。
4. 配对逻辑以后端为准，前端不负责“最终匹配判定”。
5. 批处理触发时，未匹配到同名 CSV 的文档直接跳过，并返回跳过原因清单。

## 2. 核心设计原则

1. 前端只负责“传文件”，后端负责“配对、校验、入库、可追踪”。
2. 为避免用户把文档和 CSV 传到不同批次，`session` 对前端可透明，后端自动管理。
3. 同一用户 + 同一知识库同时只允许 1 个 `open` 会话，避免批次污染。
4. 批处理前做一次后端最终配对与校验，保证 MinIO 入库质量。

## 3. 上传会话（Session）策略

## 3.1 会话划分

1. 维度：`(created_by_user_id, knowledge_base)`。
2. 规则：若存在 `open` 会话则复用；否则自动新建。
3. 生命周期：`open -> syncing -> completed/failed`，可补充 `cancelled`。

## 3.2 建议新增表：`upload_sessions`

字段建议：

1. `id TEXT PRIMARY KEY`
2. `knowledge_base TEXT NOT NULL`
3. `created_by_user_id BIGINT NOT NULL`
4. `status TEXT NOT NULL` (`open|syncing|completed|failed|cancelled`)
5. `doc_file_count INT NOT NULL DEFAULT 0`
6. `csv_file_count INT NOT NULL DEFAULT 0`
7. `paired_count INT NOT NULL DEFAULT 0`
8. `unpaired_count INT NOT NULL DEFAULT 0`
9. `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
10. `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`

索引建议：

1. `UNIQUE (knowledge_base, created_by_user_id) WHERE status = 'open'`
2. `INDEX (created_by_user_id, created_at DESC)`

## 4. 本地目录与文件命名

目录结构建议：

```text
knowledge_data/
  docs/{session_id}/
  csv/{session_id}/
```

规则：

1. 一个 `session_id` 内，`docs` 下文档文件名必须唯一；重复上传同名文档返回 `409`。
2. 一个 `session_id` 内，`csv` 下 CSV 文件名必须唯一；重复上传同名 CSV 返回 `409`。
3. 文档与 CSV 的配对键：`basename`（不含扩展名，建议统一小写比较）。

## 5. 数据模型调整（在现有 documents 基础上）

## 5.1 `documents` 新增字段

1. `upload_session_id TEXT`（关联 `upload_sessions.id`）
2. `pair_status TEXT`  
   值建议：`pending_pair|paired|missing_csv|invalid_csv|ambiguous_pair`
3. `pair_error TEXT`
4. `csv_file_name TEXT`（已匹配 CSV 文件名）
5. `csv_md5 TEXT`（可选）

说明：现有 `local_file_path/local_csv_path/sync_status/sync_mode` 可继续复用。

## 5.2 新增表：`uploaded_csv_files`

用于承接“先传 CSV、后传文档”的场景。

字段建议：

1. `id TEXT PRIMARY KEY`
2. `upload_session_id TEXT NOT NULL`
3. `knowledge_base TEXT NOT NULL`
4. `file_name TEXT NOT NULL`
5. `base_name TEXT NOT NULL`
6. `local_csv_path TEXT NOT NULL`
7. `csv_md5 TEXT NOT NULL`
8. `parse_status TEXT NOT NULL` (`valid|invalid`)
9. `parse_error TEXT`
10. `metadata_json JSONB`（可缓存解析结果）
11. `created_by_user_id BIGINT NOT NULL`
12. `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`
13. `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`

索引建议：

1. `UNIQUE (upload_session_id, file_name)`
2. `INDEX (upload_session_id, base_name)`

## 6. 接口改造方案

## 6.1 保留：单对同步上传（sync）

接口：`POST /api/v1/knowledge/documents`  
规则：

1. 仍要求 `file + metadata_csv` 单对上传。
2. 上传成功后立即同步 MinIO。
3. 若同名不匹配/CSV 不合法，直接 `422`。

## 6.2 新增：批量上传文档接口

接口：`POST /api/v1/knowledge/documents/batch-upload/doc-files`

入参（`multipart/form-data`）：

1. `files[]`（多个文档）
2. `knowledge_base`（可选，默认 `default`）

行为：

1. 自动获取/创建当前 `open session`。
2. 文件落地到 `knowledge_data/docs/{session_id}/`。
3. 创建 `documents` 记录，初始 `pair_status=pending_pair`。
4. 立即尝试与同会话 CSV 匹配，更新为 `paired/missing_csv/ambiguous_pair`。

## 6.3 新增：批量上传 CSV 接口

接口：`POST /api/v1/knowledge/documents/batch-upload/csv-files`

入参（`multipart/form-data`）：

1. `files[]`（多个 CSV）
2. `knowledge_base`（可选，默认 `default`）

行为：

1. 自动获取/创建当前 `open session`。
2. 文件落地到 `knowledge_data/csv/{session_id}/`。
3. 解析并校验 CSV，写 `uploaded_csv_files`（`valid/invalid`）。
4. 触发同会话配对刷新，更新 `documents.pair_status`。

## 6.4 新增：会话配对状态查询

接口：`GET /api/v1/knowledge/documents/batch-upload/session/current?knowledge_base=default`

返回建议：

1. `session_id`
2. `doc_file_count/csv_file_count/paired_count/unpaired_count`
3. `unmatched_documents[]`（含 `document_id/file_name/pair_status/pair_error`）
4. `orphan_csv_files[]`（只传 CSV 但无对应文档）

## 6.5 调整：批处理同步触发

接口：`POST /api/v1/knowledge/documents/batch-sync/start`

新增参数建议：

1. `knowledge_base`（可选，默认 `default`）
2. `strict_pairing`（默认 `false`）

触发逻辑：

1. 取当前 `open session` 下 `pair_status='paired'` 的文档进入上传队列。
2. `strict_pairing=true` 时，若存在未配对文档，直接 `422`，不执行同步。
3. `strict_pairing=false` 时，未配对文档跳过，写入任务 `skipped_documents`。
4. 每个已配对文档读取对应 CSV 元数据，决定 MinIO `object_key`（优先 `minio_object_key`）。

## 6.6 任务状态查询扩展

接口：`GET /api/v1/knowledge/documents/batch-sync/tasks/{task_id}`

建议补充字段：

1. `session_id`
2. `skipped_count`
3. `skipped_documents[]`（`document_id/file_name/reason`）

## 7. 配对与校验规则

## 7.1 配对规则

1. 以 `basename` 匹配（`xxx.pdf` <-> `xxx.csv`）。
2. 文档同名冲突或 CSV 同名冲突标记 `ambiguous_pair`。
3. 有文档无 CSV：`missing_csv`。
4. 有 CSV 但解析失败：对应文档标记 `invalid_csv`。
5. 有 CSV 无文档：保留在 `uploaded_csv_files`，查询接口展示为 `orphan_csv_files`。

## 7.2 CSV 校验规则（沿用现有）

1. UTF-8 编码。
2. 必填：`title, year, type`。
3. `type=paper` 要求 `journal`。
4. `type=conference` 要求 `conference`。
5. `scenes` 仅允许 `engineer|researcher|student|support`。
6. `language` 仅允许 `zh|en`。

## 8. 与现有实现的差异点

当前已实现：

1. 单接口 `file + metadata_csv` 上传。
2. `sync|batch` 两种模式。
3. 批处理任务状态已 DB 化。

本次新增重点：

1. 增加“两个独立批量上传接口”（文档与 CSV 分离）。
2. 增加 `upload_session` 自动归并逻辑。
3. 增加文档级 `pair_status` 与 `pair_error`。
4. 批处理触发支持“跳过未配对文档并返回清单”。

## 9. 分阶段实施（可直接排期）

## Phase 1：Schema + Repository

1. 新增 `upload_sessions`、`uploaded_csv_files` 表。
2. `documents` 增加 `upload_session_id/pair_status/pair_error/csv_file_name`。
3. Repository 增加：
   - `get_or_create_open_session(...)`
   - `save_batch_doc_files(...)`
   - `save_batch_csv_files(...)`
   - `refresh_session_pairing(...)`
   - `get_current_session_summary(...)`

验收：

1. DB 迁移可重复执行。
2. 能查询到当前会话及配对统计。

## Phase 2：Router 接口

1. 增加两个批量上传接口。
2. 增加当前会话状态查询接口。
3. 调整 `batch-sync/start` 支持 `strict_pairing` 与 `session` 语义。

验收：

1. 可先传 docs 再传 csv，也可先传 csv 再传 docs。
2. `pair_status` 随上传实时刷新。

## Phase 3：Batch Sync 执行器

1. 仅处理 `paired` 文档。
2. 上传前读取 CSV 元数据并生成/校验 MinIO `object_key`。
3. 任务结果输出 `success/failed/skipped` 全量明细。

验收：

1. 未配对文档不会误入 MinIO。
2. 任务状态与文档状态一致。

## Phase 4：测试与文档

1. 更新 `tests/api/test_rest_api.py` 增加 docs/csv 分离上传用例。
2. 新增专项 smoke 测试脚本（分离接口场景）。
3. 更新 API 对接文档与前端调用顺序。

验收：

1. 回归通过。
2. 前端可按“选文件夹 -> 两次批量上传 -> 手动触发同步”稳定跑通。

## 10. 前端调用顺序（最终建议）

1. 调“批量上传文档”接口（整包文档）。
2. 调“批量上传 CSV”接口（整包 CSV）。
3. 调“当前会话状态”接口，查看 `paired/unpaired`。
4. 调“批处理同步”接口（建议默认 `strict_pairing=false`）。
5. 根据任务状态查看 `skipped_documents` 并补传缺失 CSV。

---

结论：该方案可直接落地，且兼容你现在的 `sync` 能力，不会影响已有单文件上传链路。
