# 审核后端登录管理增量接入方案（仅登录模块）

## 1. 目标与边界

### 1.1 目标
在“审核后端主体已完成”的前提下，仅新增用户登录管理能力：
- 固定账号体系
- JWT 登录态
- 基础权限字段透传
- 最小侵入接入现有审核接口

### 1.2 非目标
- 不重做现有审核业务模块（QA/检索/统计主体逻辑不重写）
- 不改动现有数据库核心业务表结构（除新增用户与可选 token 黑名单表）
- 不引入复杂 IAM、SSO、OAuth

---

## 2. 增量接入原则
- **最小改动**：新增 `auth` 模块，尽量不改原有 controller/service。
- **兼容优先**：接口前缀沿用现有 ` /api/v1 `，只新增 `/auth/*`。
- **可灰度上线**：先“可用但不强制鉴权”，验证后再切为强制鉴权。
- **角色保持前端兼容**：前端当前识别 `admin | reviewer | viewer`，后端若内部使用 `observer`，响应时映射为 `viewer`。

---

## 3. 数据库增量设计

## 3.1 用户表（按 prompt 要求）

```sql
CREATE TABLE IF NOT EXISTS users (
  id            BIGSERIAL PRIMARY KEY,
  username      VARCHAR(64) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  name          VARCHAR(100) NOT NULL,
  role          VARCHAR(16) NOT NULL CHECK (role IN ('admin', 'reviewer', 'observer')),
  status        VARCHAR(16) NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'disabled')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

> 说明：`role` 存 `observer`，对前端响应时映射 `viewer`（若你不想映射，也可把前端角色改为 `observer`）。

## 3.2 （可选）登出黑名单表
如果希望 `POST /auth/logout` 真正失效 token，建议新增：

```sql
CREATE TABLE IF NOT EXISTS jwt_blacklist (
  jti          UUID PRIMARY KEY,
  user_id      BIGINT REFERENCES users(id),
  expires_at   TIMESTAMPTZ NOT NULL,
  revoked_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

---

## 4. 固定账号初始化（seed）
新增 seed 脚本，仅初始化固定内部账号（示例）：
- `admin-01 / <初始密码>`
- `reviewer-01 / <初始密码>`
- `observer-01 / <初始密码>`

实现要求：
- 密码必须通过 `bcrypt` 存储 `password_hash`
- seed 可重复执行（upsert，不重复插入）
- 生产环境首登后建议改密

---

## 5. 新增接口契约（仅登录管理）

前缀统一：`/api/v1`

## 5.1 POST `/auth/login`
请求：
```json
{
  "username": "reviewer-01",
  "password": "123456"
}
```

成功响应：
```json
{
  "token": "<jwt>",
  "username": "reviewer-01",
  "role": "reviewer",
  "name": "审核员A",
  "expires_in": 28800
}
```

失败：
- `401` 用户名或密码错误
- `403` 账号被禁用

## 5.2 GET `/auth/me`
Header：`Authorization: Bearer <jwt>`

响应：
```json
{
  "id": 2,
  "username": "reviewer-01",
  "name": "审核员A",
  "role": "reviewer",
  "status": "active",
  "created_at": "2026-03-22T00:00:00Z"
}
```

## 5.3 POST `/auth/logout`
Header：`Authorization: Bearer <jwt>`

响应：
```json
{ "success": true }
```

> 若未实现黑名单机制，可先做幂等空操作（前端删除本地 token 即可）。

---

## 6. JWT 与中间件增量

## 6.1 JWT 建议
- 签名算法：`HS256`
- 有效期：`8h`
- Claims：`sub`、`username`、`role`、`jti`、`iat`、`exp`

## 6.2 新增中间件
- `authMiddleware`：解析并校验 token，挂载 `req.user`
- `rbacMiddleware(roles[])`：校验角色

---

## 7. 对现有审核接口的最小接入方式

### 7.1 推荐分两步
1. **阶段1（灰度）**：保留原接口可访问，同时支持带 token 调用
2. **阶段2（切换）**：将关键审核接口改为强制 `authMiddleware`

### 7.2 建议保护的接口
- `GET /qa/pending`
- `GET /qa/{id}`
- `PUT /qa/{id}`
- `GET /qa/stats`
- `GET /qa-pairs`

### 7.3 角色策略（建议）
- `admin`：全部
- `reviewer`：读 + 提交审核
- `observer(viewer)`：只读

---

## 8. 审核操作日志与登录模块关系
你当前主体已有审核日志能力时，不需要重构；只需要在写日志时补充：
- `actor_user_id`
- `actor_username`

来源直接取 `req.user`（由 JWT 中间件注入）。

---

## 9. 与当前前端的对齐点（重点）

当前前端登录链路期望字段：
- `token`
- `username`
- `role`

因此后端登录响应必须至少包含以上三项。`name/expires_in` 可扩展返回。

角色兼容：
- 若后端返回 `observer`，前端会被路由守卫判无权限（当前前端使用 `viewer`）
- 解决方式：后端在响应层把 `observer -> viewer`

---

## 10. 增量实施步骤（1~2天）

### Day 1
- 新增 users migration + seed
- 新增 auth service/controller/repo
- 打通 `/auth/login`、`/auth/me`

### Day 2
- 新增 `/auth/logout`
- 接入 auth/rbac middleware 到现有路由
- 联调前端登录 + 鉴权访问

---

## 11. 验收清单
- [ ] 固定账号可登录（正确密码 200，错误密码 401）
- [ ] 返回 JWT，前端可存储并携带请求
- [ ] `/auth/me` 可返回当前用户信息
- [ ] `/auth/logout` 可正常响应
- [ ] 关键审核接口可识别登录态
- [ ] `observer` 与前端 `viewer` 角色兼容已处理
- [ ] 审核日志中可记录操作者身份

---

## 12. 需要后端同学最终确认的唯一事项
请确认角色字段最终对外值：
- 若坚持 `observer`，前端需改角色枚举
- 若保持前端不改，后端响应层统一映射为 `viewer`（推荐）
