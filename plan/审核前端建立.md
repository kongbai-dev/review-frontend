# 半导体智能知识库审核前端建立方案（Vue3 + Tailwind CSS v4 + Vite）

## 1. 建设目标与范围

### 1.1 目标
- 构建一个面向“问答审核”的高可用前端系统，支撑 `pending -> reviewed` 的审核闭环。
- 提供角色化能力：管理员、审核员、观察员。
- 对接现有 REST API，优先覆盖审核主链路与统计看板。

### 1.2 本期范围（MVP）
- 登录与会话管理（本地联调可先用假登录，保留 JWT 接口层）。
- 待审核列表、审核详情、提交审核、审核历史、基础统计。
- 公共能力：筛选检索、表单校验、错误处理、权限守卫、操作审计信息展示。

### 1.3 非目标（后续迭代）
- 富文本编辑器、批量 AI 辅助改写、实时协同编辑、国际化多语言。

---

## 2. 技术方案

### 2.1 前端技术栈
- 框架：Vue 3（Composition API）
- 构建：Vite 7+
- 样式：Tailwind CSS v4（设计变量 + 原子类）
- 路由：Vue Router 4
- 状态：Pinia
- 网络层：Axios（统一拦截器）
- 表单校验：Vee-Validate + Zod
- 表格/虚拟列表：TanStack Table + Vue Virtual Scroller（数据量大时）
- 图表：ECharts（统计页）
- 测试：Vitest + Vue Testing Library + Playwright
- 代码质量：ESLint + Prettier + Stylelint + Husky + lint-staged

### 2.2 为什么采用 Tailwind v4（而非重 UI 组件库）
- 审核场景强调信息密度和响应速度，Tailwind 更利于快速定制。
- 能与设计 token 深度绑定，便于后续品牌化和主题切换。
- 避免组件库样式覆盖冲突，减少维护复杂度。

## 4. 页面与核心流程

### 4.1 页面清单
- `/login`：登录页（支持 mock / JWT）
- `/reviews`：待审核列表页
- `/reviews/:id`：审核详情页（主战场）
- `/history`：审核历史页
- `/dashboard`：统计页

### 4.2 审核主流程
1. 审核员进入待审列表，按主题/场景/置信度筛选。
2. 打开详情页，查看 `question/answer` 与关联 `fragments`。
3. 编辑问题、答案、标签、置信度、审核备注。
4. 提交后调用 `PUT /api/qa/{id}`，状态更新为 `reviewed`。
5. 返回列表并刷新计数；失败时保留草稿并提示重试。

### 4.3 API 映射（按当前文档）
- 列表：`GET /api/qa/pending?limit=20`
- 详情：`GET /api/qa/{id}`
- 提交审核：`PUT /api/qa/{id}`
- 统计：`GET /api/qa/stats`
- 历史（建议后端补充或复用）：`GET /api/v1/qa-pairs` / `GET /api/v1/qa-pairs/{qa_pair_id}`

## 5. 数据模型与前端约束

### 5.1 关键实体（前端 TypeScript）
- `QAPair`：id, question, answer, topics, scenes, confidence, status, reviewer, reviewed_at, review_notes, version
- `Fragment`：id, fragment_type, content, page_start, page_end, meta
- `ReviewPayload`：question, answer, topics, scenes, confidence, review_notes, status='reviewed'

### 5.2 业务规则
- 置信度范围：`0.5 ~ 1.0`（步长 0.01）
- 提交前必填：question、answer、topics(>=1)、scenes(>=1)、review_notes
- 并发编辑冲突：基于 `version` 做乐观锁（冲突时提示“页面已过期，请刷新”）

## 6. 权限与安全

### 6.1 角色权限矩阵
- 管理员：查看全部、分配任务、查看统计、审核。
- 审核员：领取/处理已分配任务、提交审核。
- 观察员：只读访问。

### 6.2 安全策略
- 统一请求拦截器注入 `Authorization`（后续上云可直接启用）。
- 路由守卫 + 按钮级权限控制。
- 统一错误码处理：`401/403/409/422/500/503`。
- 前端不存储敏感信息，token 使用短时策略（可放 HttpOnly Cookie，视后端实现）。

## 7. UI 与交互规范（Tailwind v4）

### 7.1 设计基线
- 使用 CSS 变量定义语义色：`--color-bg --color-surface --color-primary --color-danger --color-warning`。
- 信息密集型布局：左列表 + 右详情（桌面）；移动端改为分步流程。
- 可读性优先：长文本支持 diff 高亮、折叠、关键字段固定。

### 7.2 关键交互
- 自动保存草稿（本地 `localStorage`，按 `qaId` 隔离）。
- 片段展开时显示页码、来源、定位信息。
- 提交成功后 toast + 列表项状态即时更新。
- 网络失败自动退避重试（幂等接口可重试）。

## 8. 工程质量与测试

### 8.1 质量门禁
- `npm run lint`、`npm run typecheck`、`npm run test` 必须通过。
- PR 必须包含：接口联调截图、关键交互录屏、风险说明。

### 8.2 测试覆盖建议
- 单测：数据转换、校验器、store action。
- 组件测试：审核表单、片段折叠、权限可见性。
- E2E：登录 -> 列表 -> 审核提交 -> 统计刷新。

## 9. 开发计划（建议 2 周）

### 第 1 周
- Day 1-2：项目初始化、路由/状态/请求层、Tailwind 主题变量。
- Day 3-4：待审列表 + 详情页静态搭建。
- Day 5：接入 `GET /api/qa/pending`、`GET /api/qa/{id}`。

### 第 2 周
- Day 6-7：审核提交与校验、错误处理、草稿能力。
- Day 8：统计页、历史页。
- Day 9：权限控制、性能优化（列表虚拟滚动/缓存）。
- Day 10：测试补齐、联调回归、发布验收。

---

## 10. 验收标准
- 可独立完成审核流程：查看待审 -> 编辑 -> 提交 reviewed。
- 页面首屏加载 < 2s（内网环境，冷启动除外）。
- 关键页面无阻断级错误（P0/P1）。
- 与后端接口字段对齐，无手工改包依赖。
- 审核数据可追溯（详情页可查看来源片段和版本信息）。

---

## 11. 实施建议（落地顺序）
1. 先实现审核主链路（列表、详情、提交），不要先做复杂统计。
2. 统一接口契约与错误码，再做权限和体验增强。
3. 将“任务分配”和“审核历史”作为第二批功能，避免影响首版上线。
4. 联调期固定每日报错归类：接口契约问题 / 业务规则问题 / 前端状态问题。

以上方案与《半导体智能知识库系统》和 `rest_api_spec.md` 对齐，可直接作为审核前端实施蓝图。
