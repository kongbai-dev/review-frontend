# 文档管理页与接口收发优化设计方案（v2）

更新时间：2026-04-13  
依据文档：

---

## 1. 目标与结论

后端接口已从“单接口 `upload_mode=sync|batch`”演进为“双轨模型”：

1. `sync`：继续走 `POST /api/v1/knowledge/documents`（单对 `file + metadata_csv`）。
2. `batch`：改为分离上传 + session 驱动：
   - `POST /batch-upload/doc-files`
   - `POST /batch-upload/csv-files`
   - `GET /batch-upload/session/current`
   - `POST /batch-sync/start`
   - `GET /batch-sync/tasks/{task_id}`

因此前端文档管理页需要从“一个上传面板”升级为“**实时上传区 + 批处理工作区**”。

---

## 2. 页面信息架构（DocumentManagePage）

建议将页面分为 5 个主区块：

1. 顶部统计与筛选区（保留）
2. 实时上传区（Sync Upload）
3. 批处理工作区（Batch Workspace）
4. 文档列表区（保留）
5. QA 手动生成区（保留）

---

## 3. UI 方案

## 3.1 实时上传区（Sync）

表单字段：

1. 文档文件 `file`（必填）
2. 元数据 CSV `metadata_csv`（必填）
3. `knowledge_base`（默认 `default`）
4. `document_type`（可选）
5. `title`（可选）
6. `subdir`（可选）

交互规则：

1. 文档与 CSV basename 不一致时前端阻断提交。
2. `upload_mode` 前端固定传 `sync`（或不传，按后端默认）。
3. 成功后立即刷新：`stats + list + session summary`。

## 3.2 批处理工作区（Batch）

### Step A：批量上传文档

- 接口：`POST /batch-upload/doc-files`
- 入参：`files[] + knowledge_base`
- 结果展示：
  - `total_files/accepted_count/rejected_count`
  - `items[]`（逐文件状态：`stored/duplicate/rejected` 等）

### Step B：批量上传 CSV

- 接口：`POST /batch-upload/csv-files`
- 入参：`files[] + knowledge_base`
- 结果展示：
  - `items[]` 中的 `invalid/duplicate/rejected` 明细

### Step C：查看当前 session 配对状态

- 接口：`GET /batch-upload/session/current?knowledge_base=...`
- 展示字段：
  - `session_id/status`
  - `doc_file_count/csv_file_count/paired_count/unpaired_count`
  - `unmatched_documents[]`
  - `orphan_csv_files[]`

### Step D：触发批处理同步

- 接口：`POST /batch-sync/start`
- 请求参数：
  - `knowledge_base`
  - `min_batch_size`
  - `max_wait_seconds`
  - `max_docs`
  - `max_workers`
  - `include_failed`
  - `strict_pairing`

UI 要点：

1. 默认 `strict_pairing=false`，提供开关。
2. 若启用 `strict_pairing=true`，并存在 `unpaired_count>0`，前端先二次确认。

### Step E：任务状态轮询

- 接口：`GET /batch-sync/tasks/{task_id}`
- 轮询间隔：3 秒，终止状态：`skipped|completed|failed`
- 展示字段：
  - `queued/processed/success/failed/skipped`
  - `failed_documents[]`
  - `skipped_documents[]`（重点展示 reason）

## 4. 接口收发重构设计

## 4.1 API 层方法拆分（document.api.ts）

新增/调整方法：

1. `uploadSyncDocument(payload)` -> `POST /knowledge/documents`
2. `batchUploadDocFiles(files, knowledgeBase)` -> `POST /knowledge/documents/batch-upload/doc-files`
3. `batchUploadCsvFiles(files, knowledgeBase)` -> `POST /knowledge/documents/batch-upload/csv-files`
4. `getCurrentBatchSession(knowledgeBase)` -> `GET /knowledge/documents/batch-upload/session/current`
5. `startBatchSync(payload)` -> `POST /knowledge/documents/batch-sync/start`
6. `getBatchSyncTask(taskId)` -> `GET /knowledge/documents/batch-sync/tasks/{task_id}`
7. `startQaGeneration(payload)`（保留）
8. `getQaGenerationTask(taskId)`（保留）

## 4.2 类型新增（domain.ts）

建议新增：

1. `BatchUploadFileItem`
2. `BatchUploadResponse`
3. `UploadSessionSummaryResponse`
4. `SessionUnmatchedDocumentItem`
5. `SessionOrphanCsvItem`
6. `BatchSyncStartRequest`（补充 `knowledge_base`、`strict_pairing`）
7. `BatchSyncTaskStatusResponse`（补充 `session_id`、`skipped_count`、`skipped_documents`）

## 4.3 Store 状态（document.store.ts）

建议新增状态：

1. `batchUploadDocResult`
2. `batchUploadCsvResult`
3. `currentSessionSummary`
4. `batchSyncTask`
5. `batchSyncPolling`

建议动作：

1. `uploadSyncPair()`
2. `batchUploadDocs()`
3. `batchUploadCsvs()`
4. `refreshCurrentSessionSummary()`
5. `triggerBatchSync()`
6. `pollBatchSyncTask()`

## 5. 文档列表区优化（配合新后端语义）

在列表中建议增加字段展示（后端返回时启用）：

1. `sync_status`
2. `pair_status`
3. `pair_error`
4. `upload_session_id`（可放在详情 tooltip）

列表动作建议：

1. 下载（保留）
2. 生成 QA（保留，单文档）
3. 删除（按后端能力可恢复）

## 6. 失败场景与交互策略

## 6.1 常见错误码映射

1. `401`：清 session 并跳登录
2. `403`：隐藏/禁用写操作按钮
3. `409`：在批量上传结果中标记重复项，不中断整批 UI
4. `422`：展示后端 `detail`（CSV 结构/配对/strict 校验失败）
5. `500/502`：保留任务上下文，允许重试

## 6.2 关键体验要求

1. 批量上传结果必须“逐文件可见”。
2. `skipped_documents` 必须“可读到 reason”。
3. 批处理执行前后都要展示 `session` 统计变化。

---

## 7. 与现有前端实现的差异与迁移

当前实现（上一版）是“文档+CSV 队列逐对上传（可选 batch/sync）”。  
新契约下需要迁移为：

1. 保留“逐对上传”但仅用于 `sync`。
2. 删除“逐对 batch 上传”的前端语义。
3. 新增“文档批量上传”和“CSV 批量上传”两个独立入口。
4. 增加“session 配对状态”面板作为批处理前置检查。

迁移顺序建议：

1. 先落 API/类型/store。
2. 再重构上传组件 UI（拆成 Sync 与 Batch 两块）。
3. 再接入任务轮询和 session 状态刷新。
4. 最后补充 E2E（docs->csv->sync）路径。

---

## 8. 页面交互流程（推荐）

### 流程 A：实时上传

1. 选择文档 + CSV
2. 提交 sync 上传
3. 成功后刷新列表与统计

### 流程 B：批处理上传

1. 上传 doc files（可多次）
2. 上传 csv files（可多次）
3. 刷新/查看当前 session summary
4. 触发 batch sync（可选 strict）
5. 轮询任务直到完成
6. 根据 skipped/failed 明细补传后重试

---

## 9. 验收标准

1. 页面能同时支持 sync 单对上传与 batch 分离上传。
2. batch 场景下，前端能展示 session 的 paired/unpaired 真实状态。
3. `strict_pairing=true` 的失败提示明确、可复现。
4. 任务状态可见 `skipped_documents` 明细。
5. 接口收发字段与 OpenAPI 一致，不再混用旧 `upload_mode=batch` 语义。
