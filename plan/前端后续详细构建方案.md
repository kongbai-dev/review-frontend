# 前端后续详细构建方案

## 1. 文档目的

基于现有前端代码、[`前端后续API补充设计.md`](D:\javascrip\review-frontend\plan\前端后续API补充设计.md) 和 [`answer.md`](D:\javascrip\review-frontend\plan\answer.md) 中已经确认的信息，整理一份可以直接指导开发落地的增量构建方案。

本方案聚焦两个新增页面：

1. 文档管理页
2. 成员排行页

方案默认沿用当前项目技术栈：

- Vue 3
- TypeScript
- Vite
- Vue Router
- Pinia
- Axios
- Tailwind CSS v4

## 2. 已确认的前提

以下内容已经从 `answer.md` 中得到确认，本方案按这些前提直接展开，不再继续做开放式假设。

### 2.1 接口归口方式

- 接口规范以 [`前端后续API补充设计.md`](D:\javascrip\review-frontend\plan\前端后续API补充设计.md) 为唯一来源。
- 前端需要把新增接口统一封装到 `services/api` 层。
- 页面、组件、store 中不直接写死接口路径。
- 接口地址统一通过 `config.ts` 管理，基础地址和环境相关配置继续沿用 `.env + API_CONFIG` 的方式。

### 2.2 权限策略

- 本期不针对新页面做复杂权限矩阵设计。
- 新页面先按“登录即可访问”处理，前端不做细粒度角色差异化。
- 为后续权限细化预留 `route meta` 和按钮级显隐扩展点。

这意味着首版实现建议：

- `/documents` 对所有已登录用户可见
- `/members` 对所有已登录用户可见
- 文档上传、下载等操作先不按角色做前端限制

### 2.3 上传交互形态

- 上传交互风格参考当前 `ManualQaForm` 的展开方式。
- 页面头部保留一个“上传文档”按钮。
- 点击按钮后，在页面中展开一个独立的上传面板组件，而不是直接弹系统文件框或先做复杂拖拽区。

也就是说，文档管理页的上传区应采用：

1. 顶部按钮触发
2. 内联面板展开
3. 面板内完成文件选择、提交、取消

### 2.4 下载方式

- 后端使用 MinIO 存储原始文档。
- 下载方式采用后端生成临时签名 URL。
- 前端拿到 URL 后直接触发浏览器下载，不接管二进制流拼装。

这是首版最合理的方案，因为实现简单、浏览器兼容性稳定、后续和对象存储对接也清晰。

### 2.5 成员排行默认规则

- 默认排序规则：按 `username` 首字母升序。
- 页面需要支持排序字段切换。
- 页面需要支持升序和降序切换。

因此成员排行页的最小排序能力应为：

- 默认排序：`username asc`
- 按上传文档数排序
- 按审核 QA 数排序
- 支持 `asc / desc`

### 2.6 成员名称展示规则

- 页面统一展示 `username`
- 首版不强依赖 `display_name`

如果后端未来补了 `display_name`，可以作为增强字段加入，但不作为当前页面的必要条件。

### 2.7 文档详情和删除

- 文档详情和文档删除本期不做
- 但要在模块设计上预留对接空间

这意味着本期：

- 表格操作列只放“下载”
- API 层和配置层可以预留 `resource` / `delete` 方法
- 页面和组件不需要真正渲染详情、删除入口

### 2.8 数据规模

- 文档列表规模按“几百到上千份”设计
- 成员排行规模目前大约十几人

对实现方式的直接影响是：

- 文档列表必须走服务端分页
- 成员排行无需做复杂分页和虚拟列表
- 成员排行首版可以一次性拉取完整列表，再在前端排序

### 2.9 视觉风格

- 新页面风格与当前前端保持一致
- 不引入另一套全新设计语言
- 沿用现有卡片、表格、按钮、状态样式和页面布局习惯

## 6. 总体技术方案

### 6.1 分层原则

- `config.ts` 负责接口路径集中配置
- `services/api` 只负责请求与响应解析
- `stores` 负责页面共享状态、加载态和错误态
- `pages` 负责页面拼装
- `components/business` 负责业务组件拆分

### 6.2 接口归口原则

所有新增接口统一从 [`前端后续API补充设计.md`](D:\javascrip\review-frontend\plan\前端后续API补充设计.md) 取用，不在本方案中维护第二份冲突定义。

本方案只规定前端如何接入这些接口：

- endpoint 放在 `API_CONFIG.ENDPOINTS`
- 请求封装放在 `services/api`
- 页面不直接拼接 URL

### 6.3 路由策略

新增两个路由：

- `/documents`
- `/members`

由于本期不做复杂权限区分，建议这两个路由先和当前审核页一样，要求“已登录即可访问”。

### 6.4 风格策略

沿用当前项目的页面组织方式：

- 顶部标题 + 说明 + 刷新按钮
- 主内容采用 `surface-card` / `surface-panel` 风格
- 表格和卡片使用现有颜色变量和按钮体系

## 7. 文档管理页详细方案

## 7.1 页面定位

- 路由：`/documents`
- 页面组件：`src/pages/DocumentManagePage.vue`
- 页面职责：承接文档统计、文档上传、文档列表、文档下载

## 7.2 页面结构

文档管理页建议拆成 4 个区域：

1. 页面头部
2. 统计卡片区
3. 上传操作区
4. 文档列表区

### 7.2.1 页面头部

内容建议：

- 标题：文档管理
- 说明：展示知识库文档概况和上传入口
- 操作按钮：
  - 上传文档
  - 刷新

### 7.2.2 统计卡片区

展示 3 个核心指标：

- `document_count`
- `fragment_count`
- `qa_count`

建议复用统计页现有卡片样式，避免新页面视觉脱节。

### 7.2.3 上传操作区

这一块按照 `ManualQaForm` 的交互风格设计，不走“默认常驻大拖拽框”的方案。

建议交互如下：

1. 页面头部点击“上传文档”
2. 通过 `showUploadPanel` 控制 `DocumentUploadPanel` 展开
3. 上传面板内完成文件选择、提交、取消
4. 提交成功后自动收起或保持展开，取决于实际体验

建议上传面板包含：

- 文件选择控件
- 已选文件名展示
- 支持格式说明
- 提交按钮
- 取消按钮
- 上传中 loading 状态
- 错误提示

### 7.2.4 文档列表区

建议使用标准表格而不是卡片流布局。

表格字段：

- 文档名称 `file_name`
- 上传时间 `uploaded_at`
- 上传用户 `uploaded_by`
- 文件类型 `file_type`
- 文件大小 `file_size`
- 切片数量 `fragment_count`
- 生成 QA 数 `qa_count`
- 操作 `actions`

操作列本期只放：

- 下载

需要预留但不在本期渲染的能力：

- 查看详情
- 删除文档

## 7.3 上传交互细节

### 7.3.1 上传入口

建议页面本地状态如下：

```ts
const showUploadPanel = ref(false);
```

建议交互方式如下：

```vue
<button type="button" class="btn btn-ghost btn-sm" @click="showUploadPanel = !showUploadPanel">
  上传文档
</button>

<DocumentUploadPanel
  v-if="showUploadPanel"
  :loading="documentStore.uploading"
  @submit="handleUpload"
  @cancel="showUploadPanel = false"
/>
```

这和当前 `ManualQaForm` 的交互方式一致，用户学习成本最低。

### 7.3.2 上传校验

当前已明确的限制是“界面风格参考 `ManualQaForm`”，但没有额外给出文件大小限制，因此首版建议：

- 前端只校验文件是否已选择
- 前端根据 `accept` 限制基本类型
- 文件过大、格式不合法等强校验交给后端
- 前端负责透传后端错误信息

支持格式先按当前项目已有约定：

- `.pdf`
- `.doc`
- `.docx`
- `.txt`
- `.md`

### 7.3.3 上传完成后的刷新策略

上传成功后执行：

1. 刷新文档统计
2. 刷新文档列表第一页
3. 视情况关闭上传面板
4. 给出成功提示

## 7.4 分页与性能策略

由于文档规模预计为几百到上千份，因此文档页必须采用服务端分页。

建议：

- 默认 `page_size = 20`
- 支持切换分页
- 默认按 `uploaded_at desc`
- 首版不做前端全量缓存
- 上传成功后只刷新第一页，而不是全量重新拉取所有数据

## 7.5 下载策略

下载流程按“后端临时签名 URL”实现：

1. 前端调用下载接口或获取下载 URL
2. 后端返回可直接访问的临时地址
3. 前端直接使用浏览器打开 / 跳转该地址下载

前端不建议自行处理文件流拼装，这会增加复杂度，也和当前后端存储方式不匹配。

## 7.6 本期不做但需预留

- 文档详情弹窗 / 详情页
- 文档删除确认框
- 文档状态筛选
- 拖拽上传增强交互

预留方式：

- `document.api.ts` 保留 `getDetail` / `remove` 方法位置
- `config.ts` 保留 `DOCUMENT_RESOURCE` 方法
- 表格操作列设计成可扩展结构，不写死只有一个按钮

## 8. 成员排行页详细方案

## 8.1 页面定位

- 路由：`/members`
- 页面组件：`src/pages/MemberRankingPage.vue`
- 页面职责：展示成员上传文档数和审核 QA 数，并支持排序

## 8.2 页面结构

成员排行页建议拆成 3 个区域：

1. 页面头部
2. 排序控制区
3. 成员排行表格区

### 8.2.1 页面头部

内容建议：

- 标题：成员排行
- 说明：展示成员上传和审核贡献情况
- 刷新按钮

### 8.2.2 排序控制区

需要两个控件：

- 排序字段
- 排序方向

排序字段建议值：

- `default`
- `uploaded_docs`
- `reviewed_qa`

排序方向建议值：

- `asc`
- `desc`

其中：

- `default` 对应 `username asc`
- 首版依然允许配合 `asc / desc` 切换

### 8.2.3 成员排行表格区

表格字段建议：

- 排名 `rank`
- 用户名 `username`
- 审核 QA 数 `reviewed_qa_count`
- 上传文档数 `uploaded_document_count`

可选字段：

- 最近活跃时间 `last_active_at`

由于当前已明确展示规则使用 `username`，首版不需要额外设计“姓名 + 用户名”双列样式。

## 8.3 数据规模与实现策略

成员数量目前约十几人，因此首版不需要做复杂分页。

建议实现策略：

- 进入页面时获取一次完整排行数据
- 排序优先在前端 store 中完成
- 如果后端已经提供 `sort_by` / `order`，则 store 可以直接透传并刷新

这样做的好处是：

- 首版实现简单
- 用户切换排序时响应更快
- 后端接口稍有变化时，前端仍然有兜底能力

## 8.4 排序规则

已确认规则如下：

- 默认：按 `username` 升序
- 可按上传文档数排序
- 可按审核 QA 数排序
- 每种排序均支持 `asc / desc`

建议在前端做稳定排序，数值相同的时候使用 `username` 作为次排序键。

## 8.5 本期不做但需预留

- 成员详情页
- 组织维度筛选
- 时间范围筛选
- 多维排行榜切换

## 9. API 接入与配置方案

## 9.1 单一接口来源

接口定义统一引用 [`前端后续API补充设计.md`](D:\javascrip\review-frontend\plan\前端后续API补充设计.md)。

本方案不再维护另一套冲突的字段说明，只规定前端如何接入。

## 9.2 config.ts 改造原则

新增 endpoint 全部加入 `API_CONFIG.ENDPOINTS`，建议包括：

```ts
ENDPOINTS: {
  ...,
  DOCUMENT_STATS: '/knowledge/documents/stats',
  DOCUMENT_LIST: '/knowledge/documents',
  DOCUMENT_UPLOAD: '/knowledge/documents',
  DOCUMENT_RESOURCE: (id: string) => `/knowledge/documents/${id}`,
  DOCUMENT_DOWNLOAD: (id: string) => `/knowledge/documents/${id}/download`,
  MEMBER_RANKINGS: '/analytics/member-rankings'
}
```

约束：

- 页面不直接拼 URL
- `services/api` 只从 `API_CONFIG.ENDPOINTS` 取路径
- 环境切换仍然依赖：
  - `VITE_API_BASE_URL`
  - `VITE_API_TIMEOUT`
  - `VITE_USE_MOCK`

### 9.2.1 是否继续通过 env 控制单个 endpoint

本期不建议把每个新增接口都拆成单独 env 变量。

原因：

- 当前接口路径已经趋于稳定
- 继续给每个 endpoint 建 env 会让配置过度分散
- 现有项目更适合“baseURL 走 env，路径常量走 config.ts”的方式

## 9.3 API 模块拆分

建议新增：

- `src/services/api/document.api.ts`
- `src/services/api/member.api.ts`

### 9.3.1 document.api.ts 职责

- 获取文档统计
- 获取文档列表
- 上传文档
- 获取下载地址
- 预留详情 / 删除方法

### 9.3.2 member.api.ts 职责

- 获取成员排行
- 封装排序参数

## 9.4 上传请求方式

上传接口使用 `multipart/form-data`。

实现建议：

- 使用 `FormData`
- 将文件 append 到 `file`
- 如果后端仍保留 `knowledge_base` 字段，则默认传 `default`
- 不强依赖前端传 `uploaded_by`

## 9.5 下载请求方式

下载接口建议返回临时签名 URL。

前端实现建议：

1. `document.api.ts` 获取下载地址
2. `document.store.ts` 调用后直接触发跳转
3. 页面层只负责按钮点击，不处理下载细节

## 10. 类型与状态管理方案

## 10.1 domain.ts 需要新增的类型

建议新增：

- `DocumentStats`
- `KnowledgeDocument`
- `DocumentListQuery`
- `UploadDocumentResult`
- `MemberRankingItem`
- `MemberRankingSortField`
- `SortOrder`
- `MemberRankingQuery`

其中成员名称保留字段建议如下：

```ts
export interface MemberRankingItem {
  user_id: string;
  username: string;
  reviewed_qa_count: number;
  uploaded_document_count: number;
  last_active_at?: string;
}
```

首版不强依赖 `display_name`。

## 10.2 types/api.ts 建议补充

由于文档列表需要稳定分页，建议把通用列表响应补成分页版结构，至少兼容：

```ts
export interface PagedListResponse<T> {
  items: T[];
  total: number;
  page: number;
  page_size: number;
}
```

这样文档列表、成员排行后续如需分页都可以直接复用。

## 10.3 document.store 方案

建议状态：

```ts
interface DocumentState {
  stats: DocumentStats;
  items: KnowledgeDocument[];
  total: number;
  page: number;
  pageSize: number;
  loading: boolean;
  uploading: boolean;
  error: string;
}
```

建议 action：

- `fetchStats()`
- `fetchList(page?: number)`
- `upload(file: File)`
- `download(document: KnowledgeDocument)`
- `refresh()`

关键行为：

- 上传成功后刷新统计和第一页列表
- 下载由 store 执行，不把临时 URL 处理散落到组件里

## 10.4 member.store 方案

建议状态：

```ts
interface MemberState {
  items: MemberRankingItem[];
  sortBy: MemberRankingSortField;
  order: SortOrder;
  loading: boolean;
  error: string;
}
```

建议 action：

- `fetchRankings()`
- `setSort(sortBy, order)`
- `refresh()`
- `applyLocalSort()`

由于成员数量小，`applyLocalSort()` 非常值得保留，可以避免每次切换排序都依赖后端。

## 11. 组件与页面拆分方案

## 11.1 建议新增组件

建议新增以下业务组件：

## 16. 风险与兜底方案

## 16.1 接口字段波动风险

虽然接口主方案已经有文档，但联调时仍可能出现字段名变化。

兜底方式：

- 所有解析都收口在 `services/api`
- 页面不直接消费原始后端结构
- store 只拿领域模型

## 16.2 上传限制未完全量化

目前没有明确给出统一文件大小限制。

兜底方式：

- 首版前端只做扩展名和是否选择文件的校验
- 文件大小超限由后端返回错误
- 前端原样展示错误信息

## 16.3 成员排行接口实现差异

后端可能返回已排序列表，也可能只返回原始列表。

兜底方式：

- store 中保留本地排序能力
- 后端有排序就透传
- 后端没有排序就本地排序

## 16.4 下载地址时效风险

签名 URL 可能有时效限制。

兜底方式：

- 每次点击下载都重新请求最新地址
- 不在前端长期缓存下载 URL

建议实际开发顺序如下：
