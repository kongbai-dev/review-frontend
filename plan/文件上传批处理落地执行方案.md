# 文件上传批处理落地执行方案（backend_api）

更新时间：2026-04-12

## 已落地接口（2026-04-12）

1. 上传：`POST /api/v1/knowledge/documents`
2. 批处理触发：`POST /api/v1/knowledge/documents/batch-sync/start`
3. 批处理状态：`GET /api/v1/knowledge/documents/batch-sync/tasks/{task_id}`
4. 手动 QA 生成：`POST /api/v1/knowledge/documents/qa-generation/start`
5. QA 任务状态：`GET /api/v1/knowledge/documents/qa-generation/tasks/{task_id}`

当前实现约束：
1. 上传时要求 `file` 与 `metadata_csv` 同名主文件名。
2. `upload_mode` 支持 `sync` 与 `batch`。
3. 上传接口不再自动生成 QA，需手动触发 QA 生成接口。

## 1. 目标与范围

本方案针对当前 `testagent/backend_api` 的文档上传链路，完成以下改造：

1. 上传接口不再直接以 MinIO 成功为前置条件。
2. 上传时强制要求“文档 + 同名 CSV 元数据”成对提交。
3. 文档先落地到项目根目录 `knowledge_data`。
4. MinIO 同步支持两种模式：
   - `sync`：实时上传（低并发场景）
   - `batch`：按 `最小批量 N + 最长等待 T` 批量上传（高并发场景）
5. QA 生成从上传接口中拆出，改为手动触发接口并可指定生成条数。
6. 文档列表、删除、下载接口继续围绕 MinIO，但兼容“未同步到 MinIO”的文档。

## 2. 当前实现基线（仓库现状）

当前上传逻辑位于：
- `testagent/backend_api/routers/v1_documents.py`

当前流程是单接口串行完成：
1. 收文件
2. 直接上传 MinIO
3. 解析切片
4. 写 Weaviate
5. 自动生成 QA
6. 完成入库状态

当前问题：
1. 上传与 MinIO 强耦合，MinIO 波动会阻断整条上传业务。
2. QA 生成与上传耦合，上传时延不可控。
3. 不支持“文档先落地、后批量同步 MinIO”的运营模式。
4. 无“同名 CSV 强约束”的接口级校验。
5. 下载接口当前为 `501`，删除逻辑未区分“已同步/未同步”状态。

## 3. 目标架构

## 3.1 目录与文件组织

项目根目录新增（或约定）：

```text
knowledge_data/
  papers/
  conferences/
  manuals/
  books/
  code/
  data/
```

每个业务文档与同名 CSV 同目录，例如：

```text
knowledge_data/papers/2024/ieee_ted_001.pdf
knowledge_data/papers/2024/ieee_ted_001.csv
```

## 3.2 文档状态机

`documents.status` 建议扩展并统一语义：

1. `received`：已落地本地目录，等待同步或处理。
2. `sync_pending`：待批量上传 MinIO。
3. `syncing`：批处理任务上传中。
4. `synced`：已上传 MinIO。
5. `qa_pending`：待手动触发 QA 生成。
6. `indexed`：分片与 QA 已完成。
7. `failed`：处理失败（含错误码、错误信息）。
8. `deleted`：逻辑删除。

## 4. 接口改造方案

## 4.1 文档上传接口（改造）

保留现有路径：`POST /api/v1/knowledge/documents`

新规则：
1. 必填：`file`（文档）与 `metadata_csv`（同名 CSV）。
2. 校验：文件名主干必须一致（如 `a.pdf` 与 `a.csv`）。
3. 新增字段：`upload_mode=sync|batch`，默认 `sync`。
4. 上传动作：
   - 落地文档与 CSV 到 `knowledge_data`
   - 解析 CSV 元数据入库
   - 仅在 `sync` 模式尝试立即上传 MinIO
   - 不再自动触发 QA 生成

## 4.2 批处理触发接口（新增）

1. `POST /api/v1/knowledge/batch-sync/start`
   - 可选参数：`batch_size`、`max_wait_seconds`、`max_workers`
   - 返回 `batch_task_id`
2. `GET /api/v1/knowledge/batch-sync/tasks/{task_id}`
   - 返回进度：总数、成功数、失败数、重试数、开始/结束时间

触发方式：
- 由前端按钮触发接口。
- 后端服务内部执行任务，不建议直接暴露任意脚本执行。

## 4.3 QA 手动生成接口（新增）

1. `POST /api/v1/qa-pairs/generation`
   - 入参：`document_id`、`target_count`、`mode=append|replace`
2. `GET /api/v1/qa-pairs/generation/tasks/{task_id}`
   - 返回生成进度与失败原因

规则：
1. 上传接口不再生成 QA。
2. QA 生成接口按 `target_count` 生成并写入 `qa_pairs`。
3. 支持幂等请求键（如 `X-Request-ID`）。

## 4.4 文档下载与删除（补齐）

1. 下载：
   - `synced`：返回 MinIO 预签名 URL
   - `sync_pending/received`：可选返回本地文件下载流或提示“未同步”
2. 删除：
   - 先删 MinIO（若已同步）
   - 再删本地文档与 CSV
   - 最后逻辑删除数据库记录

## 5. 批处理执行策略（N + T）

## 5.1 不全盘扫描原则

不扫描整个 `knowledge_data`，统一从数据库挑选：
- `status in ('sync_pending','failed')`
- 且 `retry_count < max_retry`
- 按 `uploaded_at` 升序

## 5.2 触发条件

满足任一条件即触发一批上传：
1. 待同步数量 `>= N`
2. 最早待同步文档等待时间 `>= T`

## 5.3 并发策略

1. 使用线程池（I/O 密集）并发上传 MinIO。
2. 每个文档独立事务更新状态与错误信息。
3. 单文档失败不影响整批任务继续。

## 5.4 失败与重试

1. 文档级失败：标记 `sync_failed`，记录 `last_error_code` / `last_error_message`。
2. 批任务支持手动重试。
3. 重试采用退避间隔（如 1m/5m/15m）。

## 6. 数据模型调整（最小可落地）

建议在 `documents` 表新增字段：
1. `local_file_path TEXT`
2. `local_csv_path TEXT`
3. `sync_mode TEXT` (`sync|batch`)
4. `sync_status TEXT` (`sync_pending|syncing|synced|sync_failed`)
5. `sync_attempts INT DEFAULT 0`
6. `sync_last_error TEXT`
7. `minio_uploaded_at TIMESTAMPTZ`
8. `qa_status TEXT` (`qa_pending|qa_generating|qa_done|qa_failed`)

建议新增唯一索引（避免重复入库）：
- `UNIQUE (knowledge_base, file_md5)`（对 `status <> 'deleted'` 生效）

说明：若数据库版本不支持部分索引，可先用应用层去重 + 常规唯一索引替代。

## 7. CSV 校验与去重规则

## 7.1 CSV 校验

1. 编码：UTF-8。
2. 必填字段：`title`, `year`, `type`。
3. 条件字段：
   - `type=paper` 必填 `journal`
   - `type=conference` 必填 `conference`
4. `scenes` 必须在允许集合：`engineer|researcher|student|support`。
5. `language` 必须是 `zh|en`。

## 7.2 去重规则

按优先级执行：
1. 文件 MD5 精确去重（主规则）
2. 同知识库下 `title + year + type` 弱去重（告警，不强拦）

## 8. 分阶段实施计划

## Phase A（接口解耦）
1. 上传接口改为“落地 + CSV 校验 + 入库”，去掉自动 QA。
2. 增加 `upload_mode`。
3. 增加必要字段迁移。

交付标准：
- 上传成功不依赖 MinIO。
- 文档状态能区分 `sync_pending/synced`。

## Phase B（批处理）
1. 新增批处理触发与状态查询接口。
2. 后端实现 N+T 批处理执行器。
3. 增加失败重试与任务日志。

交付标准：
- 不全盘扫描，按库内状态队列处理。
- 支持并发上传与失败隔离。

## Phase C（QA 手动生成）
1. 新增 QA 生成触发接口。
2. 新增 QA 任务状态查询。
3. 上传接口完全移除 QA 生成逻辑。

交付标准：
- 前端可按文档与条数触发 QA 生成。

## Phase D（下载/删除/回归）
1. 补齐下载接口。
2. 删除接口支持本地 + MinIO 双清理。
3. 完成回归测试与文档更新。

交付标准：
- 文档生命周期闭环完整。

## 9. 测试与验收清单

1. 上传同名校验：非同名文档+CSV 必须 `422`。
2. `sync` 模式：上传后 MinIO 可见对象。
3. `batch` 模式：上传后仅本地落地，批处理触发后再进 MinIO。
4. 批处理只处理新任务，不扫描全盘。
5. 手动 QA：指定条数可落库，任务状态可追踪。
6. 删除：本地文件、CSV、MinIO、DB 状态一致。
7. 去重：重复文件应返回冲突或复用已有记录。
8. 下载：已同步文档返回有效链接；未同步有明确反馈。

## 10. 可落地性评估

总体结论：**可落地，建议分阶段推进，先做 Phase A + B。**

评分（满分 5）：
1. 技术可行性：4.5
2. 实施复杂度：3.5
3. 业务收益：4.5
4. 风险可控性：4.0

主要优势：
1. 上传链路与外部对象存储解耦，稳定性明显提升。
2. 批处理模式可提升大批量导入吞吐。
3. QA 生成从上传剥离后，接口响应更可控。

主要风险：
1. 状态机变复杂，若状态定义不统一会出现“卡状态”。
2. 本地落地目录需要运维保障（磁盘、备份、权限）。
3. 批处理并发需严格控制重试与幂等，避免重复上传。

风险缓解：
1. 统一状态枚举与状态迁移规则。
2. 引入任务级监控与告警（失败率、重试次数、任务时长）。
3. 先灰度启用 `batch`，默认仍为 `sync`。
