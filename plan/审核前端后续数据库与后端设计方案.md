# 审核前端后续数据库与后端设计方案

## 1. 文档目的

本文基于 [docs/前端后续API补充设计.md](D:/pythoncodes/AI_TCAD/docs/前端后续API补充设计.md) 中提出的新增接口需求，给出当前项目在 PostgreSQL 数据模型、内部审核后端、仓储层与迁移路径上的后续设计方案。

本文只覆盖 **内部审核前端** 所需的后端与数据库设计，不覆盖未来真正面向最终用户的前端账号体系与业务流程。

## 2. 设计边界与默认决策

### 2.1 设计边界

- 内部审核前端继续是独立的内部系统。
- 知识库/RAG 能力仍然是整个项目的核心域能力。
- 本文重点设计内部审核前端所需的 `/api/v1` 接口背后的数据库与后端实现，不要求一次性重写整个 RAG 主服务。

### 2.2 默认决策

为了让方案能落地，本文先做以下默认决策：

1. 内部审核后端继续以 [testagent/backend_api](D:/pythoncodes/AI_TCAD/testagent/backend_api) 为基础扩展，作为内部审核 API 服务，建议运行在 `8001`。
2. 现有 [testagent/api](D:/pythoncodes/AI_TCAD/testagent/api) 继续保留为知识库核心/用户侧能力服务，建议继续运行在 `8000`。
3. 审核前端需要的新增接口统一由内部审核后端提供，即审核前端后续只连一套 `/api/v1` API。
4. 内部审核后端和知识库核心服务共享同一套 PostgreSQL、MinIO、Weaviate，但应共享领域模型，不应继续各自维护互相割裂的数据表。
5. `uploaded_by` 一律从登录态推导，不允许前端显式传入。
6. `PUT /api/v1/qa-pairs/{id}` 采用“全量可编辑字段 + 乐观锁 version 校验”的模式，`version` 不匹配时返回 `409 Conflict`。
7. 文档下载接口采用“后端生成 MinIO 签名 URL 并 302 跳转”方案，不直接在应用层回传大文件流。

## 3. 当前项目现状与主要问题

当前仓库中已经存在三套并行的数据模型：

### 3.1 知识库审核数据模型

定义位置： [testagent/api/repository.py](D:/pythoncodes/AI_TCAD/testagent/api/repository.py)

主要表：

- `documents`
- `fragments`
- `qa_pairs`
- `qa_fragment_link`
- `review_history`

这套表已经能支撑当前 `/api/qa/*`、`/api/documents/*`、`/api/search`。

### 3.2 内部认证数据模型

定义位置： [testagent/backend_api/repositories/auth_repository.py](D:/pythoncodes/AI_TCAD/testagent/backend_api/repositories/auth_repository.py)

主要表：

- `kb_users`
- `kb_auth_token_revocations`
- `kb_review_logs`

这套表只服务于当前 `/auth/*` 与 `/review-logs`。

### 3.3 旧 RAG 元数据模型

定义位置： [testagent/storage/metadata_repo.py](D:/pythoncodes/AI_TCAD/testagent/storage/metadata_repo.py)

主要表：

- `kb_documents`
- `kb_qa_pairs`

这套表目前仍被 [testagent/rag/vector_store.py](D:/pythoncodes/AI_TCAD/testagent/rag/vector_store.py) 和 [testagent/rag/rag_service.py](D:/pythoncodes/AI_TCAD/testagent/rag/rag_service.py) 使用。

### 3.4 当前主要问题

1. **存在多套事实源**  
   同一个项目内同时存在 `documents` 与 `kb_documents`、`qa_pairs` 与 `kb_qa_pairs`，后续功能一旦扩展，极易出现“前端改的是一套表，检索读的是另一套表”。

2. **认证与审核主数据没有真正打通**  
   当前 `qa_pairs.reviewer` 只是字符串，不是外键，无法稳定支持成员排行、最近活跃时间、上传人与审核人的关联分析。

3. **审核日志表设计与主表不兼容**  
   `kb_review_logs.qa_pair_id` 目前是 `BIGINT`，而当前知识库主表 `qa_pairs.id` 是 `TEXT` UUID，二者天然不兼容，不能作为后续正式方案延伸。

4. **文档表字段不足以支撑新增页面**  
   当前 `documents` 缺少：
   - `uploaded_by`
   - `knowledge_base`
   - `file_size`
   - `file_md5`
   - `file_type`
   - `status`
   - `fragment_count`
   - `qa_count`

5. **缺少导入任务模型**  
   新设计中明确提到了 `IngestionTask`，但当前主业务表中没有正式的任务表来表达文档处理状态。

6. **QA 主表缺少任务分配语义**  
   当前只有 `reviewer` 字符串，没有“当前分配给谁”和“最后由谁审核”的拆分字段，无法支撑批量分配任务。

7. **统计型接口没有稳定的数据基础**  
   例如：
   - 文档总览统计
   - 成员排行
   - 最近活跃时间
   - 按上传人统计

   这些都需要更稳定的结构化字段与审计事件。

## 4. 推荐的整体后端演进方向

## 4.1 服务定位

### `testagent/api` 的定位

- 面向知识库核心能力与后续用户侧能力
- 可继续保留：
  - 检索
  - RAG 摘要
  - 未来用户侧查询接口

### `testagent/backend_api` 的定位

- 演进为 **内部审核后端**
- 负责审核前端所需的统一 `/api/v1` 接口：
  - `/api/v1/auth/*`
  - `/api/v1/knowledge/documents*`
  - `/api/v1/qa-pairs*`
  - `/api/v1/analytics/*`

### 关键原则

- **共享数据库主模型**
- **接口可拆分，数据模型不能继续割裂**
- **审核前端只连内部审核后端**

## 4.2 数据模型策略

推荐把以下表定义为后续正式主表：

- `kb_users`
- `kb_auth_token_revocations`
- `documents`
- `ingestion_tasks`
- `fragments`
- `qa_pairs`
- `qa_fragment_link`
- `qa_review_events`

推荐逐步淘汰或只读保留：

- `kb_review_logs`
- `review_history`
- `kb_documents`
- `kb_qa_pairs`

## 5. 目标数据模型设计

## 5.1 `kb_users`

说明：内部审核成员表，沿用现有表名，避免不必要的大迁移。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGSERIAL PK | 用户主键 |
| username | TEXT UNIQUE NOT NULL | 登录名 |
| password_hash | TEXT NOT NULL | 密码哈希 |
| name | TEXT NOT NULL | 展示名 |
| role | TEXT NOT NULL | `admin/reviewer/observer` |
| status | TEXT NOT NULL | `active/disabled` |
| last_active_at | TIMESTAMPTZ NULL | 最近活跃时间 |
| created_at | TIMESTAMPTZ NOT NULL | 创建时间 |
| updated_at | TIMESTAMPTZ NOT NULL | 更新时间 |

说明：

- `name` 继续作为 `display_name` 的来源。
- `last_active_at` 在登录成功、上传文档、提交审核、批量分配时更新。

## 5.2 `kb_auth_token_revocations`

保留现有表即可。

用途：

- JWT 注销名单
- 支撑 `POST /api/v1/auth/logout`

## 5.3 `documents`

说明：作为知识库文档主表，建议在现有基础上扩展，不新建平行表。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT PK | 文档 ID，保持现有 UUID 字符串模式 |
| title | TEXT NOT NULL | 文档标题 |
| document_type | TEXT NOT NULL | `paper/conference/book/manual/code/data` |
| file_name | TEXT NOT NULL | 原始文件名 |
| file_type | TEXT NOT NULL | 文件扩展类型，如 `pdf/txt/docx/zip` |
| file_size | BIGINT NOT NULL | 文件大小（字节） |
| file_md5 | TEXT NULL UNIQUE | 文件 MD5，便于去重与详情展示 |
| object_key | TEXT NOT NULL | MinIO 对象路径 |
| source_path | TEXT NOT NULL | 兼容历史字段，短期内与 `object_key` 保持一致 |
| knowledge_base | TEXT NOT NULL DEFAULT 'default' | 知识库命名空间 |
| status | TEXT NOT NULL DEFAULT 'processing' | `processing/indexed/failed/deleted` |
| uploaded_by_user_id | BIGINT NULL | 上传人，FK 到 `kb_users.id` |
| uploaded_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 上传时间 |
| indexed_at | TIMESTAMPTZ NULL | 完成入库时间 |
| fragment_count | INT NOT NULL DEFAULT 0 | 片段数缓存 |
| qa_count | INT NOT NULL DEFAULT 0 | QA 数缓存 |
| last_error_code | TEXT NULL | 最近失败码 |
| last_error_message | TEXT NULL | 最近失败信息 |
| authors | JSONB NOT NULL DEFAULT '[]'::jsonb | 作者信息 |
| year | INT NULL | 出版年份 |
| doi | VARCHAR(128) NULL | DOI |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 创建时间 |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 更新时间 |

说明：

- 当前 `documents.type` 建议迁移为 `document_type`，但实现阶段可以先加新列、双写兼容，再删除旧列。
- `fragment_count` 与 `qa_count` 建议作为缓存列维护，避免文档列表每次都实时聚合。

## 5.4 `ingestion_tasks`

说明：新增，用于表达文档处理流程，补齐 `IngestionTask` 资源模型。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT PK | 任务 ID |
| document_id | TEXT NOT NULL | FK 到 `documents.id` |
| task_type | TEXT NOT NULL | 建议固定为 `document_ingestion` |
| status | TEXT NOT NULL | `processing/indexed/failed` |
| stage | TEXT NOT NULL | `uploaded/stored/parsed/fragmented/qa_generated/vectorized/completed` |
| created_by_user_id | BIGINT NULL | 任务发起人 |
| total_fragments | INT NOT NULL DEFAULT 0 | 生成片段数 |
| total_generated_qas | INT NOT NULL DEFAULT 0 | 生成 QA 数 |
| retry_count | INT NOT NULL DEFAULT 0 | 重试次数 |
| error_message | TEXT NULL | 错误详情 |
| started_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 开始时间 |
| finished_at | TIMESTAMPTZ NULL | 结束时间 |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 创建时间 |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 更新时间 |

说明：

- `documents.status` 是当前展示态。
- `ingestion_tasks.status` 是过程态。
- 内部审核前端的文档统计页可以只读 `documents.status`，文档详情页再补充读取任务明细。

## 5.5 `fragments`

保留现有表，建议补充或规范以下字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT PK | 片段 ID |
| doc_id | TEXT NOT NULL | FK 到 `documents.id` |
| fragment_type | TEXT NOT NULL | `text/table/image/code` |
| page_start | INT NULL | 起始页 |
| page_end | INT NULL | 结束页 |
| content | TEXT NOT NULL | 片段内容 |
| meta | JSONB NOT NULL | 原始附加元数据 |
| created_at | TIMESTAMPTZ NOT NULL | 创建时间 |

说明：

- 对于人工新增 QA 时传入的 `fragments`，建议允许创建“手工片段”，其 `meta.source_mode = 'manual'`。

## 5.6 `qa_pairs`

说明：作为审核工作台主表，建议在现有基础上扩展。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | TEXT PK | QA ID |
| question | TEXT NOT NULL | 问题 |
| answer | TEXT NOT NULL | 答案 |
| topics | TEXT[] NOT NULL DEFAULT '{}' | 主题标签 |
| scenes | TEXT[] NOT NULL DEFAULT '{}' | 场景标签 |
| confidence | NUMERIC(4,3) NOT NULL | 置信度 |
| source_type | TEXT NOT NULL | 文档来源类型 |
| source_mode | TEXT NOT NULL DEFAULT 'llm_generated' | `llm_generated/manual_created/imported` |
| doc_id | TEXT NULL | 关联文档 ID |
| status | TEXT NOT NULL | `pending/reviewed/deprecated` |
| assignee_user_id | BIGINT NULL | 当前分配给谁 |
| reviewer_user_id | BIGINT NULL | 最近一次审核人 |
| created_by_user_id | BIGINT NULL | 创建人 |
| reviewer | TEXT NULL | 历史兼容字段，后续可废弃 |
| reviewed_at | TIMESTAMPTZ NULL | 最近审核时间 |
| review_notes | TEXT NULL | 审核备注 |
| version | INT NOT NULL DEFAULT 1 | 乐观锁版本号 |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 创建时间 |
| updated_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 更新时间 |
| last_status_changed_at | TIMESTAMPTZ NULL | 最近状态变更时间 |

说明：

- `assignee_user_id` 用于任务分配。
- `reviewer_user_id` 用于最近审核人。
- `created_by_user_id` 用于区分 LLM 自动生成与人工录入。
- `reviewer` 字符串字段只建议短期兼容，后续接口一律以用户对象或用户名快照为准。

## 5.7 `qa_fragment_link`

保留现有设计：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| qa_id | TEXT NOT NULL | QA ID |
| fragment_id | TEXT NOT NULL | 片段 ID |

主键：

- `(qa_id, fragment_id)`

## 5.8 `qa_review_events`

说明：新增，用于统一替代 `review_history` 与 `kb_review_logs`。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGSERIAL PK | 事件 ID |
| qa_id | TEXT NOT NULL | FK 到 `qa_pairs.id` |
| event_type | TEXT NOT NULL | `created/updated/assigned/reviewed/deprecated/reopened/manual_created` |
| actor_user_id | BIGINT NULL | 操作人 |
| actor_username_snapshot | TEXT NOT NULL | 操作人用户名快照 |
| assignee_user_id | BIGINT NULL | 分配目标人，分配事件使用 |
| from_status | TEXT NULL | 原状态 |
| to_status | TEXT NULL | 新状态 |
| change_detail | JSONB NOT NULL | 字段级变化摘要 |
| old_value | JSONB NULL | 修改前快照 |
| new_value | JSONB NULL | 修改后快照 |
| request_id | TEXT NULL | 链路追踪，可选 |
| created_at | TIMESTAMPTZ NOT NULL DEFAULT NOW() | 事件时间 |

说明：

- 审核历史、成员排行、QA 详情页历史记录都应该基于这张表。
- 不建议继续扩展 `kb_review_logs`。
- 不建议继续把 `review_history` 作为唯一审计表，因为它没有稳定用户外键和事件类型语义。

## 7. 接口与数据模型映射

## 7.1 认证接口

### `POST /api/v1/auth/login`

依赖表：

- `kb_users`
- `kb_auth_token_revocations` 仅用于后续注销校验

实现建议：

- 登录成功时更新 `kb_users.last_active_at`
- JWT `sub` 使用 `kb_users.id`
- JWT 中保留 `username`、`role`、`name`

### `GET /api/v1/auth/me`

依赖表：

- `kb_users`

实现建议：

- 返回 `id/username/role/name/status/created_at`
- 同时可返回 `last_active_at` 供后续扩展

### `POST /api/v1/auth/logout`

依赖表：

- `kb_auth_token_revocations`

## 7.2 文档管理接口

### `GET /api/v1/knowledge/documents/stats`

建议统计来源：

- `document_count`: `documents` 中 `status != 'deleted'`
- `fragment_count`: `SUM(documents.fragment_count)`
- `qa_count`: `SUM(documents.qa_count)`
- `indexed_count`: `documents.status = 'indexed'`
- `processing_count`: `documents.status = 'processing'`
- `failed_count`: `documents.status = 'failed'`

### `GET /api/v1/knowledge/documents`

分页查询应直接读 `documents`，并关联：

- `kb_users` 获取 `uploaded_by`
- 必要时关联 `ingestion_tasks` 获取最近任务态

建议支持查询参数：

- `page`
- `page_size`
- `file_type`
- `document_type`
- `keyword`
- `status`
- `sort_by`
- `order`
- `knowledge_base`

建议返回字段：

- `document_id`
- `file_name`
- `file_type`
- `file_size`
- `uploaded_at`
- `uploaded_by`
- `knowledge_base`
- `status`
- `fragment_count`
- `qa_count`

### `GET /api/v1/knowledge/documents/{document_id}`

直接返回 `documents` 主表详情，可选补充最近一条 `ingestion_tasks` 记录。

### `GET /api/v1/knowledge/documents/{document_id}/download`

实现建议：

1. 从 `documents.object_key` 查到 MinIO 对象路径。
2. 调用 MinIO SDK 生成限时签名下载链接。
3. 后端返回 `302` 跳转到签名 URL。

数据库不需要新增字段，只要 `object_key/file_name/file_type` 完整即可。

### `POST /api/v1/knowledge/documents`

建议由内部审核后端统一承接上传请求，但底层复用当前文档解析、切片、QA 生成能力。

数据库写入顺序建议：

1. 写 `documents` 初始记录，`status = 'processing'`
2. 写 `ingestion_tasks`
3. 上传 MinIO
4. 写 `fragments`
5. 写 `qa_pairs`
6. 维护 `documents.fragment_count`、`documents.qa_count`
7. 更新 `documents.status = 'indexed'`
8. 更新 `ingestion_tasks.status = 'indexed'`

### `DELETE /api/v1/knowledge/documents/{document_id}`

建议语义：

- 应用层删除 MinIO 对象
- 逻辑上可以先保留软删除能力，短期可继续硬删除

如果短期继续硬删除：

- `fragments`
- `qa_fragment_link`
- `qa_pairs`
- `qa_review_events`

都要通过外键或显式事务级删除保持一致。

## 7.3 QA 工作台接口

### `GET /api/v1/qa-pairs`

建议由一套接口同时承担：

- 待审核列表
- 已审核历史列表

推荐查询参数：

- `status`
- `assignee`
- `reviewer`
- `keyword`
- `topic`
- `scene`
- `min_confidence`
- `page`
- `page_size`
- `sort_by`
- `order`

推荐字段语义：

- `assignee`: 当前任务负责人
- `reviewer`: 最近审核人

如果为了兼容前端过渡期只保留一个参数名，建议明确：

- `status = pending` 时，`reviewer` 暂按“当前分配人”解释
- `status in (reviewed, deprecated)` 时，`reviewer` 按“最近审核人”解释

但从长期设计看，**更推荐前端改用 `assignee` 与 `reviewer` 两个不同参数**。

### `GET /api/v1/qa-pairs/{qa_pair_id}`

读取：

- `qa_pairs`
- `qa_fragment_link`
- `fragments`

建议额外补充：

- `assignee`
- `reviewer`
- `source_mode`
- `doc_id`

### `PUT /api/v1/qa-pairs/{qa_pair_id}`

建议规则：

- 必须带 `version`
- 后端校验当前版本，不一致返回 `409`
- 更新后 `version = version + 1`
- 写入 `qa_review_events`

更新内容建议拆分为：

- 可编辑内容：`question/answer/topics/scenes/confidence/review_notes/status`
- 可变负责人：`assignee_user_id`
- 审核人由当前 token 自动推导，不接受前端伪造

### `GET /api/v1/qa-pairs/stats`

统计来源：

- `pending/reviewed/deprecated` 直接从 `qa_pairs.status`

建议短期只返回总数，成员维度排行交给 `/api/v1/analytics/member-rankings`。

### `POST /api/v1/qa-pairs/assignments`

实现建议：

- 批量更新 `qa_pairs.assignee_user_id`
- 批量写入 `qa_review_events`，`event_type = 'assigned'`
- 更新操作者 `last_active_at`

### `POST /api/v1/qa-pairs`

用途：

- 人工新增 QA

实现建议：

1. 后端从 token 得到 `created_by_user_id`
2. 如果请求体携带 `fragments`，则先创建手工片段
3. 创建 `qa_pairs`
4. 创建 `qa_fragment_link`
5. 写入 `qa_review_events`，`event_type = 'manual_created'`
6. 如果关联了文档，则同步增加 `documents.qa_count`

## 7.4 成员排行接口

### `GET /api/v1/analytics/member-rankings`

建议数据来源：

- `uploaded_document_count`：`documents.uploaded_by_user_id`
- `reviewed_qa_count`：`qa_review_events.event_type = 'reviewed'`
- `last_active_at`：`kb_users.last_active_at`

默认排序建议：

1. `reviewed_qa_count DESC`
2. `uploaded_document_count DESC`
3. `last_active_at DESC`
4. `username ASC`

说明：

- 这样能给出稳定且可解释的默认排行。
- 如果未来需要把“废弃判定”也算工作量，建议增加 `processed_qa_count`，而不是修改 `reviewed_qa_count` 语义。

## 8. 推荐的统计与聚合实现方式

## 8.1 文档统计

- `documents.fragment_count`
- `documents.qa_count`

## 11. 明确不建议继续沿用的做法

1. 不建议继续把审核人只存成纯字符串。  
   后续统计和权限都需要稳定用户外键。

2. 不建议继续扩展 `kb_review_logs`。  
   它与当前 `qa_pairs.id` 类型不兼容。

3. 不建议让前端传 `uploaded_by`。  
   这类字段必须由 token 推导。

4. 不建议让 `documents` 与 `kb_documents` 长期并存为两套主表。  
   这会让审核、检索、上传三条链路永远对不齐。

5. 不建议把文档计数、QA 计数完全做成实时 join 聚合。  
   文档列表页后续排序会越来越慢。

## 12. 还需要你确认的点

以下问题不阻碍当前方案成稿，但会影响实现细节，建议在正式开发前确认：

1. 内部审核后端是否确定长期使用 `8001`，并作为审核前端唯一 Base URL。
2. 未来用户前端的认证体系是否与当前 `kb_users` 完全隔离。
3. 成员排行中的“审核数量”是否只统计 `reviewed`，还是 `reviewed + deprecated` 都算工作量。
4. 文档删除是否接受短期硬删除，还是要直接进入软删除模式。
5. 旧 RAG 链路是否计划迁移到 `documents/fragments/qa_pairs` 这套主模型。

## 13. 结论

基于当前项目现状，后续最稳妥的路线不是继续叠加零散接口，而是把内部审核前端需要的能力统一沉淀到一套共享主模型上。

推荐路线可以概括为：

1. 让 `testagent/backend_api` 演进为内部审核后端，承接 `/api/v1`。
2. 让 `documents/fragments/qa_pairs` 成为知识库与审核工作台的主业务表。
3. 补齐 `kb_users`、`ingestion_tasks`、`qa_review_events` 三块关键能力。
4. 逐步淘汰 `kb_review_logs`、`review_history`、`kb_documents`、`kb_qa_pairs` 的长期主表地位。

这样可以同时解决：

- 审核前端新增页面缺少接口的问题
- 成员排行与文档统计没有稳定基础的问题
- 登录、上传、审核、检索三条链路事实源不一致的问题
- 后续用户前端接入时架构边界不清的问题

如果按这条方案推进，下一步最合适的工作是：

1. 先补数据库迁移脚本
2. 再拆仓储层
3. 最后按 `/api/v1` 增量补路由
